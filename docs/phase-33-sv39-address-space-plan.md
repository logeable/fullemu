# 第 33 阶段：Sv39 内核与用户地址空间规划

## 目标关联

用户任务已经拥有独立页表，内核可以通过 `satp` 在任务之间切换地址空间。但当前内核映像、RAM 恒等映射和用户镜像都使用 Sv39 低半部地址。继续加入运行期程序加载、用户堆或更多内存区域前，需要先说清楚地址空间的边界、映射权限和资源归属。

本阶段先盘点实现并制定地址布局约定，不改页表行为、链接地址或启动代码。下一阶段再用一个小改动把用户镜像虚拟地址从当前 RAM 恒等映射范围移开。

## 实验问题

**独立页表已经建立后，怎样区分“用户可用的虚拟地址”“内核访问物理内存的地址”和“镜像实际占用的物理位置”，并为以后扩展留出明确空间？**

## 第 33 阶段开始时的实际映射

Sv39 的低半部规范地址范围为 `0x0000000000000000..0x0000003fffffffff`，高半部为 `0xffffffc000000000..0xffffffffffffffff`。当前所有下表所列地址都在低半部；特权隔离主要依赖 PTE 的 `U` 位，而不是高低半部划分。

| 当前区域 | 虚拟地址 | 物理 backing | 当前权限与说明 |
| --- | --- | --- | --- |
| FDT 描述的 RAM | 每个 RAM 区间的物理地址恒等映射 | 同一 RAM 区间 | `SRW-`；地址空间创建时逐页映射。QEMU `virt` 当前配置的示例范围为 `0x80000000..0x88000000`，实际范围来自 FDT。 |
| 内核映像和 BSS | `__kernel_start..__bss_end` | 相同地址 | `SRWX`；覆盖 RAM 恒等映射的权限。整个范围目前可写且可执行。 |
| 用户程序映像 | `0x80400000..0x80410000` | 按程序索引分配的 64 KiB 固定物理槽 | `URWX`；所有程序链接到共同虚拟基址。当前共同虚拟基址落在 RAM 恒等映射范围内，因此该页表区域会覆盖相同虚拟地址上的 RAM 恒等映射。首个镜像槽的物理地址也从 `0x80400000` 开始。 |
| 用户栈 | `0x3fffffb000..0x3ffffff000` | 每任务独立的 16 KiB 页帧 | `URW-`；当前固定在低半部顶部附近，向低地址方向增长；栈下方留有未映射页。 |
| UART MMIO | 从 FDT 读取；QEMU 示例为 `0x10000000..0x10000100` | 相同 MMIO 地址 | `SRW-`；每个任务页表均可供 S-mode 访问，U-mode 不可访问。 |

当前映射由 `memory::address_space` 按顺序建立：先映射 FDT RAM，再映射内核、用户镜像、用户栈和 UART。相同虚拟页不能同时表示两个映射；后续映射会替换先前的叶子项。因此用户镜像与 RAM 恒等映射的地址重叠是实际的映射覆盖，不是两个可同时访问的别名。

另一个当前限制是内核映像整体映射为 `SRWX`。`.text`、`.rodata`、`.data` 和 `.bss` 尚未按链接器段边界分别设置权限。RAM 恒等映射也覆盖 FDT 报告的整个 RAM 区间，而不只覆盖分配器当前已分配的页帧。

## 目标布局约定

目标是让低半部承载用户地址空间，高半部承载内核映像和内核虚拟区域：

| 目标区域 | 规划用途 | 权限原则 |
| --- | --- | --- |
| Sv39 低半部 `0x0000000000000000..0x0000003fffffffff` | 用户程序映像、用户堆、以后可能出现的映射区和用户栈 | 仅所属任务的用户页设置 `U`；内核映像与内核私有数据不放在此区域。 |
| Sv39 高半部 `0xffffffc000000000..0xffffffffffffffff` | 内核映像、内核堆、页表访问窗口、内核栈及设备映射 | 所有任务地址空间中的内核映射保持一致，且不设置 `U`。 |

此目标不等于本阶段已经实现高半区内核运行。内核仍按 `linker.ld` 链接并在物理地址附近执行；高半区基址、物理内存直接映射策略和启动期临时映射，需在后续迁移设计中结合启动汇编、`gp`、`sp`、`stvec`、陷入帧和物理页访问逐项确定。

用户区的规划如下：

- 用户镜像继续采用统一虚拟入口，但放到不与当前 QEMU RAM 恒等映射相交的低半部区域。建议先评估 `0x40000000`，即 1 GiB；QEMU `virt` RAM 从 `0x80000000` 开始，因此这能以小改动消除当前覆盖。这个地址是教学项目的布局选择，不是 Sv39 规定值。
- 用户堆从镜像和数据末端向高地址增长；本阶段不实现堆，也不决定 `brk`/`mmap` ABI。
- 用户栈保持在低半部顶部附近并向低地址增长，栈下方保留未映射保护页。当前的固定栈地址可作为首个布局版本。
- 镜像、堆和栈的范围由地址布局契约分别约束；中间的空闲虚拟区域留给未来扩展，本阶段不分配或映射它。

## 实验结果

第 34 阶段已把用户程序共同虚拟基址从 `0x80400000` 改为 `0x40000000`，并增加运行时检查，拒绝与 FDT RAM 恒等映射相交的用户镜像虚拟范围。用户程序仍链接到共同入口，内核仍复制镜像到原有固定物理槽位。第 35 阶段再按链接器提供的页对齐段范围映射内核：`.text` 为 `SR-X`、`.rodata` 为 `SR--`、`.data` 和 `.bss` 为 `SRW-`。内核继续在低地址运行，RAM 其他部分仍按 FDT 恒等映射为 S-mode 可读写。

## 资源与映射所有权

- `frame_allocator` 管理物理页帧的分配和回收；物理地址本身不自动成为任务可用的虚拟地址。
- `task::creation` 取得用户栈、内核栈和程序镜像信息；`memory` 按输入建立虚拟到物理的映射，不拥有这些映射目标。
- 每个任务目前拥有独立根页表和用户映射。内核映射在各页表中逻辑一致，但当前由每张页表各自创建页表项，并未共享同一组高半区页表页。
- 内核物理内存访问目前依赖恒等映射。将来切换到高半区时，必须另行确定内核如何通过直接映射或显式映射访问页表、堆和页帧；不能把物理地址当作虚拟指针直接使用。
- 用户镜像当前是固定物理槽，用户栈是动态分配页帧。两者的物理生命周期和虚拟地址规划互相独立。

## 实验边界与后续顺序

本阶段只记录并核对地址布局，不修改常量、链接脚本、PTE 权限、启动地址或页表构造行为；不实现用户堆、`mmap`、按需分页或高半区迁移。

第 34 阶段已把用户程序镜像映射移出 QEMU 当前 RAM 恒等映射区；第 35 阶段已按链接器段边界建立内核的 `RX`、`R`、`RW` 权限映射。高半区内核迁移单独立项，先设计并验证启动期间的地址切换，再修改链接和运行地址。

## 验收方式

- 将本阶段表格与 `linker.ld`、`user/linker.ld`、`task::stack`、`user_program` 和 `memory::address_space` 中的实际定义逐项核对。
- 确认文档区分了当前行为与规划目标，没有把高半区映射或分段权限写成已实现能力。
- 第 34 阶段用 `make build` 和 QEMU shell、batch 启动验证新入口映射及用户栈映射；当前 shell 与 batch 程序入口应为 `0x40000000`，`memory_fault` 仍应因从 U-mode 访问 S-mode 专用的物理镜像槽而触发页故障。

## 后续连接

地址区域和所有权约定将约束后续的用户镜像映射、堆、栈和内核映射改动，并为 shell 前台运行新程序提供稳定的地址空间接口。此阶段本身不增加用户可见命令或 Linux ABI 行为。
