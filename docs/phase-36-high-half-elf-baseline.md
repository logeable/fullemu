# 第 36 阶段：高半区迁移前的 ELF 加载基线

## 目标关联

为后续把内核主体链接到 Sv39 高半区建立可重复检查的起点。启动跳板需要在分页启用前从低地址执行，并在建立映射后进入高地址内核；ELF 的入口、可加载段虚拟地址（VMA）和加载地址（LMA）决定加载器把哪些字节放在哪里。因此先确认当前产物的实际布局，避免仅凭链接脚本推测启动行为。

本阶段不切换内核运行地址，也不增加新的页表行为。

## 当前 ELF 契约

当前 `linker.ld` 将 `_start` 放在 `0x80200000`。构建产物的 ELF 程序头显示：

- ELF 入口为 `0x80200000`。
- 第一个 `PT_LOAD` 从 `0x80200000` 开始且可执行。
- 当前所有 `PT_LOAD` 的 VMA 与 LMA 相同，内核仍按低地址恒等布局链接和加载。
- `.text`、`.rodata`、`.data/.bss` 分属不同加载段，段对齐为 4 KiB。

VMA 是段运行时使用的地址；LMA 是段在加载映像中的物理装载地址。当前两者相等，未来高半区布局会让内核主体的 VMA 位于高地址、LMA 仍位于 RAM 低地址附近。低地址启动入口届时仍需位于加载器交接时可执行的位置。

## 检查方式

```sh
make inspect-kernel-elf
```

目标会先按现有流程构建，再调用 Rust 工具链提供的 `rust-readobj` 读取 ELF 头和 `PT_LOAD` 程序头。脚本只消费该工具输出的 JSON，不自行解析 ELF 格式。它检查 RISC-V 架构、入口地址、第一个可执行加载段，以及当前 VMA=LMA 的基线。

若要查看 ELF 原始程序头，可直接运行：

```sh
rust-readobj --program-headers target/riscv64gc-unknown-none-elf/release/fullemu
```

## 本阶段边界与后续连接

本阶段没有 trampoline，也没有改变启动行为；检查器描述的是当前低地址布局。接下来先设计并实现最小的低地址启动跳板和高地址映射，再将检查器的基线断言改为目标契约：入口仍可由当前加载路径抵达，内核主体的高 VMA 对应低 LMA。该阶段需要同时处理页表、`gp`、`sp`、`stvec`、内核段权限和物理地址访问，完成前不应声称高半区迁移已经支持。

## 验收记录

- `make build` 成功。
- `make inspect-kernel-elf` 应报告入口 `0x80200000`、三个 `PT_LOAD`，并确认各段 VMA=LMA、按 4 KiB 对齐。
- 本阶段不修改 QEMU 启动路径；运行时行为与此前保持一致。
