# 第 10 阶段：任务直接破坏内核调度状态

> 本文记录第 10 阶段的 S-mode 故障对照。当前默认启动已进入[第 11 阶段：U-mode 的限制与内存访问边界](phase-11-user-mode-limits.md)。

## 目标关联

第 9 阶段让内核能抢占任务，但 A、B 和内核仍都运行在 S-mode。它们没有任务级内存权限边界。这个实验不只展示 A 能改写另一个任务的数据，而是让 A 直接改写内核正在使用的调度状态，观察内核行为因此失常。要运行不受信任的用户程序，必须先阻止它直接访问内核数据。

## 学习重点

- **S-mode 任务拥有内核同级权限：** 在当前共享地址空间和无页权限保护的配置中，任务代码可以读取并写入内核数据。
- **内核状态损坏会传播到后续操作：** 调度器信任 `CURRENT_TASK`，并据此把当前陷入帧保存到对应的任务槽。被改写的索引会让内核把 A 的现场误认为 B 的现场。
- **权限隔离比约定更可靠：** 内核无法靠命名、模块边界或“任务不应该写这里”的约定阻止同权限代码写内存。

## 实验过程

1. 启动 A、B 两个任务和定时器轮转调度器；初始 `CURRENT_TASK` 为 A 的索引 `0`。
2. A 读取内核调度器的 `CURRENT_TASK`，然后把它改写为 B 的合法索引 `1`。
3. 下一次定时器中断到来时，内核相信被改写的索引，把 A 的陷入帧写进 B 的上下文槽，覆盖 B 尚未运行的初始上下文。
4. 后续调度继续恢复 A 的陷入帧，B 不再运行；内核仍在处理中断，但调度行为已经错误。

A 只写入数组范围内的合法索引，因此故障来自内核对被篡改状态的信任，而不是越界访问、栈溢出或随机崩溃。演示值和前后状态通过独立的观察变量记录，调度器不依赖这些观察变量。

## 运行与验收

```sh
make build
make run
```

串口应显示 A 读取到 `CURRENT_TASK = 0` 并将其写为 `1`。之后 A 的运行计数持续增长，B 的进度保持为 `0`；调度器会继续报告 tick，但已无法正确恢复 B。该行为表示内核调度状态被破坏，不是一个正常的隔离演示。

## 安全边界与限制

- 破坏范围严格限制为 `CURRENT_TASK`，以及调度器按该值覆盖的 B 上下文槽；不写入任意地址，不覆盖内核代码、陷入入口或有效运行栈。
- 本实验只在 QEMU 中运行，故障是预期结果。它不提供恢复机制，也不适合作为真实设备上的稳定性测试。
- A、B 仍是 S-mode 内核任务，不是 U-mode 用户进程。当前结果证明同级内核任务可以破坏内核状态，但不代表已经实现任何用户态权限边界。
- `AtomicBool` 和 `AtomicUsize` 只用于记录观察结果和避免 Rust 数据访问歧义，不会阻止 A 写入 `CURRENT_TASK`。
- 当前没有 Sv39 页表、U-mode、缺页处理或系统调用。
