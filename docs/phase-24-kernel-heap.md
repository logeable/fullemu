# 第 24 阶段：有界内核堆分配器

## 目标关联

当前任务、用户栈和页表页都由固定容量静态数组提供。后续动态任务创建需要内核运行时分配任务对象等资源；本阶段先建立一个可理解、可回收的内核堆分配器，为后续容器和动态对象管理提供基础。

## 实验问题

**内核如何在固定 RAM 区域中反复分配和回收不同大小的对象？** 分配器使用 first-fit 空闲链表，从第一个足够大的空闲块中分配；必要时拆分空闲块，释放时按地址插入并合并相邻块。

## 实现范围

- 在内核 BSS 中静态预留 256 KiB、页对齐的堆区域。它属于内核映像范围，Sv39 下仅供 S-mode 访问。
- 启动时以 `info` 级别输出链接器定义的内核映像、`.text`、`.rodata`、`.data`、`.bss` 和启动栈范围，使用不包含式结束地址并显示字节大小；堆区域位于 `.bss` 中。
- `kernel::heap` 自行实现有界分配器，不引入第三方库。每个分配块记录原始块地址和大小，以支持任意合法 `Layout` 对齐；空闲块按地址排序，释放时检查范围重叠并合并相邻块。
- 堆状态访问使用 S-mode 中断守卫：进入时原子读取并关闭 `sstatus.SIE`，离开作用域时按进入前状态恢复。嵌套守卫不会提前开启中断。
- `KernelHeapAllocator` 实现 Rust `GlobalAlloc`，将 `Layout` 请求转交给上述有界堆入口；分配失败时遵循全局分配器契约返回空指针。
- `kernel_main` 显式先调用 `kernel::heap::initialize()`，再分别运行原始分配器演示和 `Vec` 演示，使堆生命周期和实验入口清楚可见。
- 启动自检以 16 字节和 64 字节对齐请求检查分配、释放、地址复用和最终合并回单一空闲块，并输出结果日志。
- 启动自检用 `alloc::vec::Vec<u64>` 逐步加入 128 个元素，记录容量扩展和堆空闲空间变化；释放容器后验证堆恢复为单一完整空闲块。

## `allocate` 分配路径回顾

本节配合阅读 [`src/kernel/heap.rs`](../src/kernel/heap.rs) 中的 `Heap::allocate`。一次分配需要同时处理用户数据、分配器元数据和后续空闲块的布局。

### 请求大小与返回指针

- `allocate` 接收 `Layout`；`layout.size()` 是调用者请求的用户数据字节数，不包含分配头部、空闲块头部或对齐填充。本实现拒绝零大小请求。
- 成功时返回 `Some(NonNull<u8>)`，表示非空的用户数据起始地址；空间不足或地址计算溢出时返回 `None`。`NonNull` 只保证指针非空，指向有效堆空间、长度和对齐正确等条件由分配器保证。
- `required_end` 是用户数据末尾；`required_end - block_start` 覆盖从原空闲块起点到用户数据末尾的整个分配占用范围。

### 三种地址对齐

- `block_start` 必须满足 `FreeBlock` 的对齐要求。初始堆地址会检查对齐；切分后新空闲块地址为 `block_start + allocated_size`，而 `allocated_size` 会向上取整到 `align_of::<FreeBlock>()`，因此新空闲块仍然对齐。
- `payload_start` 必须满足调用者的 `layout.align()`，也必须满足 `AllocationHeader` 的对齐。代码令 `allocation_alignment = max(layout.align(), align_of::<AllocationHeader>())`。这两个对齐都是 2 的幂，较大的值是较小值的整数倍，因此满足最大值就同时满足二者。
- `AllocationHeader` 紧邻用户数据之前，地址为 `payload_start - size_of::<AllocationHeader>()`。Rust 类型大小是其对齐的整数倍；`payload_start` 按至少头部对齐的值对齐，因此减去头部大小后，头部仍然对齐。
- 这些对齐分别由不同条件保证：`allocation_alignment` 不负责对齐 `FreeBlock`。例如在 RV64 上，若块起点为 `0x1000`、`FreeBlock` 大小为 16、`AllocationHeader` 大小为 24，用户请求 64 字节对齐，则用户地址可为 `0x1040`，头部位于 `0x1028`；`0x1010..0x1028` 是头部前的对齐填充。

### 从最小位置到实际占用大小

- `minimum_payload` 先计算 `block_start + size_of::<FreeBlock>() + size_of::<AllocationHeader>()`，表示用户数据地址的下界；它尚未包含为满足对齐可能需要的填充。
- `payload_start = align_up(minimum_payload, allocation_alignment)` 得到实际用户地址。头部从 `payload_start` 向前放置，因此 `align_up` 多出的空间自然成为 `FreeBlock` 与 `AllocationHeader` 之间的填充，不会覆盖任一结构。
- `allocated_size` 将从块起点到数据末尾的长度再向上取整到 `FreeBlock` 对齐值。这使分割得到的新空闲块起点保持对齐；末尾填充也计入本次占用，释放时随整块归还。
- 边界相关的地址相加、释放时回退到头部的地址相减，以及 `align_up` 内部加法使用 `checked_add` / `checked_sub`，避免整数回绕后把堆外地址误判为有效地址。分配时无法安全计算就跳过该空闲块；释放时无法安全计算就报告无效分配。

### 切分和空闲链表链接

- 若分配后剩余空间达到 `size_of::<FreeBlock>() + align_of::<FreeBlock>()`，当前实现就把余块写成新的空闲节点；否则将无法切分的小尾部也算入本次分配块。
- 这个门槛只保证余块能容纳一个 `FreeBlock` 节点，**没有计入 `AllocationHeader` 和至少 1 字节的用户数据**。在当前 RV64 布局中，门槛是 24 字节，而最小非零分配块约需 48 字节，因此 24～47 字节的余块可能留在链表里却无法单独满足分配。它不是内存安全错误，但形成暂时不可用的碎片；相邻块释放并合并后才可能重新可用。后续若要避免这种情况，应按实际最小非零 `Layout` 计算可切分门槛。
- `replace_free_block` 用切分后余块节点替换旧空闲节点；`remove_free_block` 在整块被分配时，将旧节点从链表中摘除。链表始终按地址排序，释放时相邻的空闲块会合并；被仍在使用的块隔开的空闲区不能合并。
- 当前调用方创建余块时已经用旧节点的后继初始化 `new_block.next`，而 `replace_free_block` 又从旧节点复制一次相同的 `next`。这次写入在当前调用路径中重复；简化时可删除 `old_block` 参数及该重复写入，让调用方负责初始化新节点，辅助函数只负责替换链表链接。

## 暂不实现

- 中断守卫只屏蔽当前 hart 的 S-mode 中断，依赖项目目前单 hart 的运行约束；它不是多 hart 锁。启用 SMP 前必须加入跨 hart 同步。
- 堆容量仍固定为 256 KiB；未实现物理页分配，也不会按需向物理内存管理器扩展。
- 当前 `Vec` 实验只在启动阶段、调度开始前运行；尚未让运行期任务对象、陷入处理路径或其他内核子系统动态分配内存。
- 堆只管理内核对象，不负责物理页分配；用户程序镜像、用户栈和页表页仍由固定区域或静态数组管理。
- 暂不从 FDT 空闲内存区域动态扩展堆，也不支持多个堆区域。

## 运行与验收

```sh
make fmt-check
make build
make run
```

启动日志应报告各内核段的地址范围、原始堆分配自检结果，以及 `Vec` 的元素数、容量、扩容次数和分配/释放前后的空闲字节数。QEMU 启动时应观察到分配期间空闲空间减少，释放后恢复到 256 KiB 单一空闲块。自检在启用定时器调度前运行；此时全局中断处于关闭状态，因此 QEMU 启动验证覆盖关闭状态的恢复路径，尚未动态触发“进入前中断已开启”的恢复路径。

## 后续连接

物理页分配和动态用户地址空间仍应作为独立机制设计；后续为动态任务分配内核对象时，可以复用全局分配器，而页表页和用户栈仍需页粒度的物理内存接口。
