# 第 10 阶段：共享地址空间的隔离失败对照

## 目标关联

第 9 阶段让内核能抢占任务，但 A、B 仍运行在同一个 S-mode 地址空间。若一个任务错误地写入另一个任务的数据，当前内核没有地址空间或硬件权限机制阻止它。这个缺口直接阻碍安全运行独立用户程序，也是 shell 和 Linux 用户态程序所需的进程隔离基础。

## 学习重点

- **CPU 时间共享不等于内存隔离：** 定时器和陷入帧让内核可以切换任务，但并没有改变地址映射或访问权限。
- **内核任务的数据归属只是约定：** 本实验把一个共享标记逻辑上归给任务 B，任务 A 仍可以直接写入它，B 随后能观察到变化。
- **为何需要地址空间：** 如果每个任务可以访问所有内核可访问的内存，任务之间的“私有数据”只靠代码约定，无法抵御错误或恶意程序。

## 实现范围

- 保留第 9 阶段的两个静态栈、单 hart 定时器和轮转调度，不改变调度机制。
- 初始化一个逻辑上属于任务 B 的共享标记。任务 A 首次运行时写入不同的固定值；任务 B 持续读取并记录自己观察到了改写。
- 定时器处理路径只在观察到改写后报告一次，随后继续报告 tick 与两个任务的运行进度。
- 标记使用 `AtomicUsize`，只为让 Rust 对跨任务可见的读写有明确语义；它不会提供任务访问控制，也不是内存保护机制。
- 当前没有 U-mode、页表、地址转换或按任务设置的访问权限。本阶段不会声称具备进程隔离。

## 运行与验收

```sh
make build
make run
```

QEMU 输出应先显示 B 标记的初始值，随后显示“任务 B 观察到自己的标记已被改写”，且 A、B 的进度都继续增长。该结果证明定时器切换了执行流，却没有隔离它们可访问的内存。

## 当前边界

- A、B 都是 S-mode 内核任务，彼此信任；任务 A 的写入是受控演示，不是恶意代码沙箱。
- 静态共享标记不是任务私有内存。所谓“归 B 所有”仅是实验约定，正用于说明内核目前无法强制所有权。
- 没有物理页分配器、Sv39 页表、缺页异常处理、用户态映像或系统调用。

## 后续连接

下一阶段应引入最小的地址转换与页权限：为两个受控执行环境建立不同的虚拟地址映射，并验证任务 A 访问 B 的受保护页面会陷入，而合法访问仍可运行。这个最小保护切片将支撑用户态执行和后续系统调用边界。
