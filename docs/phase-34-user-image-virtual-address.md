# 第 34 阶段：分离用户镜像虚拟地址与物理槽位

## 目标关联

第 33 阶段的地址空间盘点发现，用户程序虚拟入口 `0x80400000` 同时位于 QEMU RAM 恒等映射区内。建立用户镜像映射时会覆盖同一虚拟页的 S-mode RAM 映射，使虚拟地址和物理镜像槽位的职责混在一起。

本阶段只移动用户程序的共同虚拟入口，不移动内核，不改变物理镜像槽、RAM 恒等映射或内核权限。它为后续增加用户堆和更精确的内核映射建立独立地址区域。

## 实验问题

**如何让用户程序继续使用共同入口，同时使入口虚拟地址不再遮蔽内核的 RAM 恒等映射？**

## 地址布局变化

| 对象 | 旧地址 | 当前地址 | 说明 |
| --- | --- | --- | --- |
| 用户程序共同虚拟入口 | `0x80400000` | `0x40000000` | 所有用户程序仍链接到同一地址；在 QEMU `virt` 上位于 RAM 恒等映射起点 `0x80000000` 以下。 |
| 用户程序物理镜像槽 | `0x80400000..0x80480000` | 不变 | 内核仍按程序索引复制到固定 64 KiB 槽位；各任务页表把自己的用户虚拟镜像映射到对应物理槽。 |
| 内核和 FDT RAM 恒等映射 | 低地址 | 不变 | 内核仍在原链接地址执行；RAM 仍按 FDT 映射为 S-mode 可读写。 |
| 用户栈 | `0x3fffffb000..0x3ffffff000` | 不变 | 仍逐页映射到任务独立的用户栈页帧。 |

新映射是 `用户虚拟地址 0x40000000 → 当前程序物理槽位`。因此用户程序不再从物理镜像地址运行，程序基址也不再覆盖 RAM 恒等映射。`0x80410000` 仍处于 RAM 恒等映射中，但 PTE 不设置 `U`；`memory_fault` 从 U-mode 读取该地址时应因权限不足产生 `LoadPageFault`。

## 构建与运行约束

- `user/linker.ld` 将共同虚拟基址固定为 `0x40000000`，并断言 `_start` 位于镜像起点、程序不超过 64 KiB。
- 所有用户 bin 使用同一链接脚本；`user/build.rs` 只负责给用户程序链接参数指定该脚本，不再生成重复记录共同基址的布局文件。
- `user-programs.manifest` 只记录程序名和原始镜像路径。内核装载器按共同地址 `0x40000000` 建立入口和虚拟镜像范围，不再从清单逐项读取或校验相同的基址。
- `memory::address_space` 将用户虚拟范围限制在 Sv39 低半部，并拒绝与 FDT 描述的 RAM 恒等映射范围重叠。物理镜像地址仍要求位于内核映像结束地址之后。

链接脚本断言负责检查 ELF 入口与镜像基址一致，地址空间初始化检查用户镜像不与 FDT RAM 恒等映射冲突。链接脚本中的基址与内核装载器中的常量共同构成构建契约；修改基址时需要同步修改两处并重新执行 shell 与 batch 验收。

## 实验边界

本阶段不更改内核链接/运行地址、不增加高半区映射、不按 `.text` 等链接段细分页权限，也不实现用户堆、`mmap` 或动态物理镜像分配。用户镜像仍以整段 `URWX` 映射，固定物理镜像槽也仍由链接脚本预留。

## 运行与验收

```sh
make fmt-check
make build
make run BOOT_MODE=shell LOG_LEVEL=info
make run BOOT_MODE=batch LOG_LEVEL=info
```

shell 应从 `0x40000000` 正常启动并能执行 `help`。batch 中各用户程序的入口日志应为 `0x40000000`，计算、I/O、协作任务和长时间 CPU 任务应保持原有行为；`memory_fault` 访问 `0x80410000` 时应报告 U-mode 页故障，其他就绪任务仍应运行完成。页表调试输出中，用户镜像虚拟范围应是 `0x40000000..0x40010000`，物理范围仍落在固定加载槽位。

## 后续连接

第 35 阶段已沿用这份地址规划，按链接器定义的 `.text`、`.rodata`、`.data` 和 `.bss` 页边界分别映射内核代码、只读数据和可写数据。高半区内核迁移仍需单独设计启动期地址切换及物理页访问方式。
