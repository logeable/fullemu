# 第 9 阶段：定时器抢占

> 本文记录第 9 阶段实验。当前默认启动还会运行[第 10 阶段：任务直接破坏内核调度状态](phase-10-kernel-state-corruption.md)。

## 目标关联

第 8 阶段让任务主动调用 `yield_now` 后才能切换。如果任务 A 永不让出，任务 B 仍然饥饿。定时器抢占让内核能在任务不配合时重新取得控制权，是后续运行多个用户进程和用户态 shell 所需的 CPU 调度基础。

## 学习重点

- **先观察中断，再用于调度：** 定时器到期产生 S-mode 中断，硬件跳转到 `stvec`，记录 `scause`、`sepc` 等 CSR；内核处理后重新设置定时器并返回。
- **异步现场比函数调用现场更完整：** 中断可以落在任意指令处，不能只保存 ABI 规定的被调用者保存寄存器。入口汇编保存全部整数寄存器和恢复所需 CSR 到被打断任务自己的栈。
- **调度器选择恢复现场：** Rust 陷入处理函数返回下一任务的陷入帧地址；汇编切换到该帧对应的栈，恢复寄存器并执行 `sret`。
- **定时器由固件提供：** 内核在 S-mode 通过 SBI TIME 扩展设置绝对到期时间，OpenSBI 转接到底层定时器。QEMU `virt` 当前时间基准为 10 MHz；本实验每 100,000 个 `time` 计数重新触发一次，约为 10 ms。

RISC-V 特权规范描述 S-mode 定时器中断和 trap CSR；SBI 规范定义 TIME 扩展及 `set_timer` 调用。当前实现走 OpenSBI 的 SBI 路径，不直接访问 QEMU 的机器态定时器寄存器。

## 实现范围

- 使用两个各自拥有 16 KiB、16 字节对齐静态栈的内核任务，固定轮转，不动态分配。
- 任务 A 和 B 都只递增自己的进度计数，不主动让出 CPU。每次定时器中断保存被打断帧并切换到另一个任务。
- `TrapFrame` 与 `trap.S` 共享固定布局：32 个整数寄存器槽位，后接 `sepc`、`sstatus`、`scause` 和 `stval`。首次运行的任务也由构造好的陷入帧经 `sret` 启动。
- SBI 调用、RISC-V 陷入现场保存和 Rust 调度决策分别放在窄接口中，避免把 CSR 与汇编细节放入任务代码。
- 每 25 个 tick 打印一次被选中的任务和 A/B 进度，以便观察两者都在推进。进度计数仅用于实验观察。

## 运行与验收

```sh
make build
make run
```

在启动摘要之后，应持续看到 tick 增长，且 A、B 的进度计数都增长。将调度器临时固定为总是返回当前陷入帧后，预期只有当前任务继续运行、另一个任务的进度停止；恢复轮转后，两者都应继续增长。任务入口中没有 `yield_now`，因此这个结果由定时器中断而非任务合作产生。

构建检查：`make build`。QEMU `virt` / OpenSBI 单 hart 运行检查：`make run`，观察串口输出。

## 当前边界

- 单 hart、两个始终可运行的内核任务；没有就绪队列、阻塞、退出、优先级或空闲任务。
- 任务共享同一地址空间，彼此没有内存保护；这还不是用户进程。
- 陷入帧不保存浮点寄存器。任务不得跨越抢占点依赖浮点寄存器中的值；若启用浮点运算，必须扩展并验证上下文保存。
- 中断处理只接受 S-mode 定时器中断；其他陷入会报告 CSR 并停机。
- 定时器间隔暂按 QEMU `virt` 的时间基准常量设置；后续支持其他平台前，应从启动平台信息读取 `timebase-frequency` 并统一时钟接口。
- 串口输出仍是轮询式；本实验只在定时器 handler 中低频输出，避免任务之间同时写控制台。

## 后续连接

抢占证明了内核可以重新取得 CPU，但当前任务都在 S-mode，与内核同级，能读写内核和彼此的数据。下一阶段直接改写调度器状态并观察其后果，再以 U-mode 和地址转换建立内核保护边界；这会为受控用户态执行、用户态陷入和系统调用铺路。
