# 项目原则与代码规范

本文档定义本仓库的设计原则和代码约定，供贡献者与编码代理共同遵循。项目架构或约定发生实质变化时应更新本文档，避免在其他文件重复维护同一套规则。

## 项目目标

使用 Rust 从零构建一个用于教学的操作系统，循序渐进地实现启动、交互式 shell，并最终通过 Linux ABI 支持广泛的 Linux 用户态程序。

项目的优先级如下：

1. **易理解：** 学习者能从一次用户操作追踪到实现该操作的内核逻辑。
2. **易维护：** 子系统职责和接口明确，改动尽量局限在相关模块。
3. **正确性：** 明确说明不变量，在边界处检查，并通过测试或可复现的手动步骤验证。
4. **逐步扩展能力：** 系统逐步具备可用 shell 和 Linux 程序支持，同时不牺牲前三项。

将 rCore 和 [Writing an OS in Rust](https://os.phil-opp.com/) 作为教学参考和思路来源，而不是必须遵循的规格。说明本项目自己的设计选择；实现应保持内部一致，并针对目标硬件和 Rust 工具链核实细节。

## 设计原则

### 通过代码结构服务教学

- 按概念与职责组织代码，而不是按一次性教程步骤或硬件寄存器组织。
- 让主要控制路径清楚可见。优先使用直接调用和小型、命名清晰的函数，避免隐式全局行为、过度依赖宏或炫技式泛型框架。
- 对不够直观的子系统，在模块级说明其用途、不变量和公开接口。
- 当抽象能表达稳定概念、维护不变量或简化测试时再引入；避免投机性分层，以及只给函数调用换名字的抽象。
- 对具有教学意义的机制，优先保留并解释其实现，不要用不透明依赖将其隐藏。

### 明确子系统边界

保持硬件机制、内核策略和用户态接口各自独立。系统发展后，应在启动与平台初始化、架构相关 CPU 与中断支持、物理与虚拟内存、任务调度、系统调用、文件系统、设备驱动和用户态程序等职责之间定义清晰接口。模块目录可以调整，但职责边界必须易于理解。

- 在可行时，将架构相关代码放在窄接口之后；共享内核逻辑不应依赖具体寄存器细节。
- 明确依赖方向和资源所有权。底层机制不应依赖 shell 行为或 Linux ABI 策略。
- 将系统调用和 Linux ABI 作为边界层：在边界处把外部约定转换为内核概念，避免 Linux 特例散布到内核各处。
- 当进程和 I/O 基础允许时，让 shell 作为用户态程序运行。如果早期阶段使用临时的内核态 monitor，应明确标记，并保留可替换的接口。
- 记录跨子系统契约，包括输入输出、所有权、错误情形和相关不变量。

### 按可验证的里程碑演进

先构建可运行的纵向切片，再逐步扩展功能。一个合理顺序是：启动与诊断；异常处理与内存；基本任务执行；系统调用与 I/O 基础；文件系统与用户态 shell；Linux ABI 覆盖与应用支持。若依赖关系要求调整顺序，应记录原因。

每个里程碑都应说明已支持的能力、明确暂不支持的部分，以及复现验证的方法。准确描述实现状态：“兼容 Linux ABI”是长期方向，不代表启动了一个程序就已经达成。兼容性应按接口和经过测试的行为逐项记录。

## Rust 代码规范

### 安全性与 `unsafe`

- 优先使用安全 Rust。仅在硬件访问、启动或运行时集成，或明确的性能需求确有必要时使用 `unsafe`。
- 将每个 `unsafe` 块缩小到必要范围。在其前紧邻添加 `// SAFETY:` 注释，说明具体哪些不变量保证操作有效；不要使用笼统保证。
- 将易失性访问、裸指针操作和架构汇编集中在小型且有文档说明的模块中。没有明确需要时，不要让原始硬件细节泄漏到其他模块。
- 为 `unsafe fn`、裸指针 API，以及带有安全不变量的类型写明安全要求，明确调用方必须履行的义务。
- 不要用 `transmute` 或未检查索引来绕过设计问题。确实需要时，说明原因以及安全表示为何不足。

### 类型、错误与状态

- 使用类型表达非法状态不可构造、资源所有权清晰。对有实际语义的状态、标识符、地址和标志位，在能减少混淆时使用枚举或 newtype。
- 避免布尔参数过多的 API 和含义不明的整数常量。为标志和状态转换命名。
- 对可恢复错误返回 `Result`，并在能够解释错误的层级定义错误类型。仅在内部不变量被破坏或早期启动确实无法继续时 panic，并提供有用上下文。
- 正常内核路径避免 `unwrap`/`expect`。如果某处按设计不可能失败，应在附近说明理由，或通过辅助函数名称表达该保证。
- 尽量减少可变全局状态。将其封装在子系统 API 后，并说明初始化顺序、中断或并发约束及生命周期假设。

### 可读性与文档

- 使用标准 Rust 格式（`rustfmt`）和惯用命名：模块、函数、变量使用 `snake_case`；类型和 trait 使用 `UpperCamelCase`；常量和静态变量使用 `SCREAMING_SNAKE_CASE`。
- 名称应体现操作系统概念。除架构或 ABI 中已约定俗成的术语外，避免难以理解的缩写。
- 注释用于解释原因、不变量、硬件限制和不明显的顺序要求；不要逐行复述直观代码。
- 为公开接口和不明显的子系统 API 编写 Rustdoc，必要时说明用途、单位或语义、错误行为和安全要求。
- 保持函数聚焦。只有在拆分能讲清概念、不变量或决策时才拆分，不要只为减少行数拆分。

### 依赖与可移植性

- 明确内核的 `no_std` 和目标平台约束。将宿主机侧工具/测试与内核运行代码区分开。
- 控制依赖数量。新增 crate 前，检查它对目标平台和 `no_std` 的支持、许可证、维护状况，以及它的作用是否便于学习者理解。
- 隔离硬件相关代码，并记录支持的目标平台、模拟器或开发板。不要声称具备尚未实现的平台可移植性。

## 改动与验证要求

- 每项改动聚焦于一个连贯问题，并保持清楚的教学脉络。避免把无关清理混入功能改动。
- 当行为、不变量、支持平台、构建步骤或用户可见命令变化时，更新相应文档。
- 为可在宿主机验证的逻辑添加或更新针对性测试；对无法通过单元测试验证的行为，提供可复现的模拟器或硬件验证步骤。构建成功不等于运行正确。
- 项目建立构建与验证命令后，沿用仓库已有命令。记录实际执行的命令和结果，并区分未测试行为与已验证行为。
- 新增 Linux ABI 行为时，说明 Linux 侧契约、当前实现范围及已知差异；条件允许时添加小型、可复现的兼容性检查。
