# 项目原则与代码规范

本文档定义本仓库的设计原则和代码约定，供贡献者与编码代理共同遵循。项目架构或约定发生实质变化时应更新本文档，避免在其他文件重复维护同一套规则。

## 项目目标

使用 Rust 从零构建一个用于教学的操作系统，循序渐进地实现启动、交互式 shell，并最终通过 Linux ABI 支持广泛的 Linux 用户态程序。

首个适配目标是 **QEMU `virt` 上的 RV64**，通过 QEMU 默认 OpenSBI 固件进入 S-mode。早期开发、调试和验证优先以该环境为基准；启动契约、串口、参数和 QEMU 版本应记录在阶段构建说明中，避免依赖未声明的平台默认值。

项目的优先级如下：

1. **易理解：** 学习者能从一次用户操作追踪到实现该操作的内核逻辑。
2. **易维护：** 子系统职责和接口明确，改动尽量局限在相关模块。
3. **正确性：** 明确说明不变量，在边界处检查，并通过测试或可复现的手动步骤验证。
4. **逐步扩展能力：** 系统逐步具备可用 shell 和 Linux 程序支持，同时不牺牲前三项。

将 rCore 和 [Writing an OS in Rust](https://os.phil-opp.com/) 作为教学参考和思路来源，而不是必须遵循的规格。说明本项目自己的设计选择；实现应保持内部一致，并针对目标硬件和 Rust 工具链核实细节。

## 设计原则

### 通过代码结构服务教学

- 按概念与职责组织代码，而不是按一次性教程步骤或硬件寄存器组织。
- 让主要控制路径清楚可见。优先使用直接调用和小型、命名清晰的函数，避免隐式全局行为、过度依赖宏或炫技式泛型框架。
- 对不够直观的子系统，在模块级说明其用途、不变量和公开接口。
- 当抽象能表达稳定概念、维护不变量或简化测试时再引入；避免投机性分层，以及只给函数调用换名字的抽象。
- 对具有教学意义的机制，优先保留并解释其实现，不要用不透明依赖将其隐藏。

### 明确子系统边界

保持硬件机制、内核策略和用户态接口各自独立。系统发展后，应在启动与平台初始化、架构相关 CPU 与中断支持、物理与虚拟内存、任务调度、系统调用、文件系统、设备驱动和用户态程序等职责之间定义清晰接口。模块目录可以调整，但职责边界必须易于理解。

- 在可行时，将架构相关代码放在窄接口之后；共享内核逻辑不应依赖具体寄存器细节。
- 明确依赖方向和资源所有权。底层机制不应依赖 shell 行为或 Linux ABI 策略。
- 将系统调用和 Linux ABI 作为边界层：在边界处把外部约定转换为内核概念，避免 Linux 特例散布到内核各处。
- 当进程和 I/O 基础允许时，让 shell 作为用户态程序运行。如果早期阶段使用临时的内核态 monitor，应明确标记，并保留可替换的接口。
- 记录跨子系统契约，包括输入输出、所有权、错误情形和相关不变量。

### 按可验证的里程碑演进

先构建可运行的纵向切片，再逐步扩展功能。实验的概念主线参考 [OSTEP](https://pages.cs.wisc.edu/~remzi/OSTEP/) 对操作系统核心内容的组织：虚拟化、并发和持久化。该组织方式用于决定“学习什么”，不要求机械照搬教材章节或实现顺序；具体顺序还要服从 RISC-V 平台约束和本项目已有代码。

1. **虚拟化：** 研究操作系统如何提供比硬件资源更有用的抽象。CPU 方向包括进程、受控执行、陷入和调度；内存方向包括地址空间、地址转换、物理页管理和分页。
2. **并发：** 研究多个执行流共享 CPU 与数据时的协调，包括线程或任务、锁、条件等待和并发错误。每种机制都应对应实际并发来源；尚无使用场景时不提前堆叠同步原语。
3. **持久化：** 研究设备 I/O、存储设备、文件和目录、文件系统组织及崩溃一致性。先建立设备与文件系统的必要边界，再逐步验证数据读写和故障行为。

启动、异常报告和 UART 等平台工作是开展上述实验的运行基础，不应和核心主题混为一谈。FDT、设备发现、链接布局等工作应服务于一个明确的虚拟化、并发或持久化实验。

shell 和 Linux ABI 是项目的集成目标与验证载体，不是替代操作系统核心主题的教学路线：shell 最终应通过进程、内存、系统调用和文件/I/O 能力运行；Linux ABI 则在这些内部抽象稳定后，按具体接口与程序逐项验证。内核态 monitor 可以用于早期实验，但不能算作最终 shell。

每个里程碑都应说明所研究的核心概念、内核新增的抽象或机制、明确暂不支持的部分，以及复现验证的方法。若实验顺序偏离核心主题的常见教学组织，应记录平台依赖或已有实现带来的原因。准确描述实现状态：“兼容 Linux ABI”是长期方向，不代表启动了一个程序就已经达成。

### 实验必须沿总体目标推进

每一次实验都必须能说明它如何推进“提供可交互的 shell，并逐步运行 Linux 用户态程序”这一总体目标。实验可以是底层机制，也可以是用户可见功能；底层机制必须明确指出它支撑的后续能力或解除的直接阻塞，不能只因为某项技术有趣或格式规范很大就扩展它。

- 优先选择依赖链上最近且尚未具备的能力。每轮结束后，应能指出内核新增了什么能力，或哪一个具体后续实验因此可以开始。
- 先做能贯通多层的最小纵向切片，再扩充边缘情况。例如，串口接收与回显直接建立交互输入路径，为行编辑和 shell 输入做准备；单独追求完整解析所有 FDT binding，若没有当前设备发现或内存管理需求，则不构成优先实验。
- 对解析器、驱动和通用框架等基础工作，先明确实际消费者和接口，再实现满足该消费者的最小正确范围。只有后续功能提出明确需求时，才扩充覆盖面。
- 学习某个机制是必要价值，但不能成为脱离项目能力目标的唯一理由。机制应放在将来可追踪的实际路径中，让学习者能从用户操作一路看到该机制的作用。
- 控制实验大小时，按一个可讲清、可验证的概念切分；不要把实验切成与后续能力没有因果联系的零碎改动，也不要把多个独立机制塞入同一实验。

提出或开始一项实验前，说明以下内容：

1. **目标关联：** 它服务于总体目标中的哪项能力，或解除哪个已知阻塞？
2. **学习重点：** 本次要理解并由项目自行实现的操作系统机制是什么？
3. **边界：** 本次明确实现什么、暂不实现什么；为什么当前范围已经足以支持下一步？
4. **验收方式：** 哪个具体行为、测试或 QEMU 操作可以证明能力已经获得？
5. **后续连接：** 哪项后续能力会直接使用本次接口或结果？

若目标关联或后续连接说不清，应先调整实验方向，不要仅为增加代码量或追求某个子系统的表面完整度而开工。

## Rust 代码规范

### 安全性与 `unsafe`

- 优先使用安全 Rust。仅在硬件访问、启动或运行时集成，或明确的性能需求确有必要时使用 `unsafe`。
- 将每个 `unsafe` 块缩小到必要范围。在其前紧邻添加中文 `// 安全性：` 注释，说明具体哪些不变量保证操作有效；不要使用笼统保证。
- 将易失性访问、裸指针操作和架构汇编集中在小型且有文档说明的模块中。没有明确需要时，不要让原始硬件细节泄漏到其他模块。
- 为 `unsafe fn`、裸指针 API，以及带有安全不变量的类型写明安全要求，明确调用方必须履行的义务。
- 不要用 `transmute` 或未检查索引来绕过设计问题。确实需要时，说明原因以及安全表示为何不足。

### 类型、错误与状态

- 使用类型表达非法状态不可构造、资源所有权清晰。对有实际语义的状态、标识符、地址和标志位，在能减少混淆时使用枚举或 newtype。
- 避免布尔参数过多的 API 和含义不明的整数常量。为标志和状态转换命名。
- 对可恢复错误返回 `Result`，并在能够解释错误的层级定义错误类型。仅在内部不变量被破坏或早期启动确实无法继续时 panic，并提供有用上下文。
- 正常内核路径避免 `unwrap`/`expect`。如果某处按设计不可能失败，应在附近说明理由，或通过辅助函数名称表达该保证。
- 尽量减少可变全局状态。将其封装在子系统 API 后，并说明初始化顺序、中断或并发约束及生命周期假设。

### 可读性与文档

- 使用标准 Rust 格式（`rustfmt`）和惯用命名：模块、函数、变量使用 `snake_case`；类型和 trait 使用 `UpperCamelCase`；常量和静态变量使用 `SCREAMING_SNAKE_CASE`。
- 名称应体现操作系统概念。除架构或 ABI 中已约定俗成的术语外，避免难以理解的缩写。
- 所有源代码注释和文档注释一律使用中文，包括 Rust 注释/Rustdoc、汇编注释、链接脚本注释及脚本注释。协议名、寄存器名、指令、API、标识符等必须原样书写的技术术语可以保留原文；不要因此把解释性句子写成英文。
- 注释用于解释原因、不变量、硬件限制和不明显的顺序要求；不要逐行复述直观代码。`unsafe` 块前使用 `// 安全性：` 开头的中文说明，具体写出保证该操作有效的不变量。
- 为公开接口和不明显的子系统 API 编写 Rustdoc，必要时说明用途、单位或语义、错误行为和安全要求。
- 保持函数聚焦。只有在拆分能讲清概念、不变量或决策时才拆分，不要只为减少行数拆分。

### 依赖与可移植性

- 明确内核的 `no_std` 和目标平台约束。将宿主机侧工具/测试与内核运行代码区分开。
- 除非确有必要，避免引入外部第三方依赖。确需依赖时，应优先选择职责非常基础、范围狭窄的库，并说明自行实现的成本为何不合理；常见、流行或方便本身不足以成为引入理由。
- 操作系统领域专用的功能和机制应尽可能在本项目中自行实现并讲清楚，以增强对原理的理解。只有当功能本身不是本项目的教学重点，且外部实现不会遮蔽关键机制时，才考虑使用第三方实现。
- 对确需采用的基础库，检查其目标平台与 `no_std` 支持、许可证、维护状况、实现范围及教学影响。必须通过针对性测试保证其正确性和稳定性，并用独立依据交叉验证，例如标准/spec、独立实现、差分测试或已知测试套件；不能仅凭依赖自身的测试或声誉认定可靠。
- 隔离硬件相关代码，并记录支持的目标平台、模拟器或开发板。不要声称具备尚未实现的平台可移植性。
- 首阶段以 QEMU RISC-V 为唯一基准平台。新增平台前，先保证基准平台的构建与启动步骤清晰可复现；硬件机型和模拟器参数应集中记录，不要散落在实现说明中。

## 改动与验证要求

- 每项改动聚焦于一个连贯问题，并保持清楚的教学脉络。避免把无关清理混入功能改动。
- 当行为、不变量、支持平台、构建步骤或用户可见命令变化时，更新相应文档。
- 涉及平台启动或硬件行为的改动，应记录并验证在首要目标 QEMU RISC-V 环境中的构建、启动或运行步骤；后续新增平台时分别标明支持状态。
- 为可在宿主机验证的逻辑添加或更新针对性测试；对无法通过单元测试验证的行为，提供可复现的模拟器或硬件验证步骤。构建成功不等于运行正确。
- 项目建立构建与验证命令后，沿用仓库已有命令。记录实际执行的命令和结果，并区分未测试行为与已验证行为。
- 新增 Linux ABI 行为时，说明 Linux 侧契约、当前实现范围及已知差异；条件允许时添加小型、可复现的兼容性检查。
