# 第 20 阶段：Sv39 用户/内核页面权限边界

## 目标关联

U-mode 已限制用户程序执行特权指令，但此前系统运行在 `satp=BARE` 下，用户程序仍能访问内核 RAM。后续动态任务和外部程序运行必须先有可由硬件执行的内存权限边界。本阶段在现有 shell 启动路径中启用 Sv39，使内核页面仅供 S-mode 访问，而当前 shell 只能访问自己的程序槽位和用户栈。

## 实验问题

**U-mode 已经有较低特权级，为什么还需要页表？** 特权级限制指令和 CSR 操作；Sv39 页表则把每个虚拟页面映射到物理页面，并由 PTE 的 U/R/W/X 权限限制访问。本阶段继续使用恒等映射，因此虚拟地址等于物理地址，新增的行为来自页面权限，而非地址搬移。

Sv39 使用三级页表，虚拟地址由三级 9 位页号索引和 12 位页内偏移组成。页表项为 8 字节，页表页为 4 KiB 并按 4 KiB 对齐；根页表物理页号与 MODE 值写入 `satp`。实现依据是 [RISC-V 特权架构规范 Sv39 章节](https://docs.riscv.org/reference/isa/_attachments/riscv-privileged.pdf)。

## 实现范围

- `kernel::memory` 使用固定静态页表页池，不申请堆内存，也不提供物理页分配器。
- 页表只映射启动后仍需访问的区域：内核映像及 BSS、当前 shell 的完整 64 KiB 用户程序槽位、当前任务的 16 KiB 用户栈，以及 QEMU `virt` UART 所在的 4 KiB 页面。以上虚拟地址均恒等映射到相同物理地址。
- 内核映像和 UART 页面只允许 S-mode 访问。当前 shell 的代码槽位允许 U-mode 读、写、执行，以兼容没有 ELF 段权限信息的原始镜像；用户栈允许 U-mode 读、写，不允许执行。
- 用户栈按 4 KiB 对齐，确保栈页面不与相邻内核状态共享页面。
- 新增 `fullemu_user_memory_fault` 用户程序，尝试从 U-mode 读取 `0x80200000`，预期触发加载页故障。内核默认入口为 `fullemu_user_shell`，可通过 `make run BOOT_PROGRAM=fullemu_user_memory_fault` 在构建时选择该示例；shell 启动其他程序仍留待后续实验。
- 在进入首个用户任务前写入 `satp` 并执行 `sfence.vma`。切换后内核 PC、内核栈和链接地址保持有效。
- 系统调用仍只接受已知程序镜像或当前用户栈范围内的缓冲区。访问这些经范围检查的地址时，内核仅在单次读写期间设置 `sstatus.SUM`，随后立即清除；其他内核代码保持默认的 U 页面访问限制。
- 取指、加载和存储页故障由现有用户任务异常路径记录 `scause`、`sepc`、`stval`，并结束当前任务。

## 暂不实现

- 每个任务仍未拥有独立根页表；当前只为默认 shell 建立一个 U-mode 映射，不代表已经隔离多个用户任务。
- 不实现动态物理页分配、地址空间复制/销毁、缺页调入、ELF 段解析、写时复制或 `fork/exec`。
- 用户程序整个固定槽位暂时是可写且可执行的；后续 ELF 加载阶段再按代码、只读数据和可写数据细分权限。
- 系统调用缓冲区校验仍局限于现有程序镜像和用户栈范围，不是通用的跨页 `copyin/copyout`。
- QEMU `virt` UART 地址仍为平台常量。FDT 在开启 Sv39 前已解析，本阶段不再访问 DTB。

## 运行与验收

```sh
make fmt-check
make build
make run
```

默认运行 `make run` 时，内核应启动 shell。运行 `make run BOOT_PROGRAM=fullemu_user_memory_fault` 时，探针应先打印即将访问的地址，随后内核报告 `LoadPageFault`，`stval` 为 `0x80200000`，并结束该用户任务。仅观察到 shell 正常启动不能证明内核页面权限正确，因此验收还应覆盖一次被拒绝的用户态访问。

## 后续连接

本阶段只建立硬件执行的单任务权限边界。下一步为不同任务建立各自的用户映射，让相同用户虚拟地址落到不同物理页面；再统一系统调用的用户内存复制接口。物理页分配和运行时装载应在这些边界清晰后单独实验。
