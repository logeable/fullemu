# 第 28 阶段：用容器管理任务记录

## 目标关联

多道程序已经有固定任务上限，但任务状态、保存的陷入帧地址和用户程序索引分散在三个平行数组中，任务数量另存在独立变量里。新增任务字段时必须同时维护这些数组及其索引关系，容易产生不一致。本阶段使用内核堆上的 `Vec<Task>` 把一项任务的调度元数据放在同一条记录中，为后续任务对象逐步取得资源所有权做准备。

## 实验问题

**当一个任务的元数据分散在多个数组中时，怎样让任务字段和任务数量具有统一、可检查的表示？**

## 实现范围

- 新增 `Task` 记录，统一保存任务状态、已保存陷入帧地址和用户程序索引。
- 使用 `Vec<Task>` 表示已经创建的任务；初始化时按任务数调用 `try_reserve_exact`，明确处理分配失败。
- 任务记录在启动阶段依次加入容器；首次进入 U-mode 后不再改变 `Vec` 长度和容量，只更新记录中的状态或陷入帧地址。
- 删除平行的任务状态、陷入帧、程序索引数组和独立任务计数，调度器通过容器长度获得任务数量。
- 用户栈和内核陷入栈仍由最多 8 组静态数组提供。任务上限、地址空间所有权、调度策略和程序加载方式均不变。

容器只管理内核任务元数据，不负责栈或物理页帧的存储。它因此不会改变页帧分配器与内核堆之间的职责边界，也不代表系统已经支持动态创建任务。

## 暂不实现

- 不动态分配或回收任务栈、用户镜像和页表。
- 不支持任务运行期间创建、销毁或复用任务索引。
- 不引入任务锁；当前实现仍假设单 hart，且任务记录只在启动路径或非嵌套陷入处理路径中访问。

## 运行与验收

```sh
make fmt-check
make build
make run LOG_LEVEL=debug
```

构建应成功；当前启动 init 和 shell 后，可输入程序名启动子进程，并观察进程对象、调度、系统调用及地址空间回收路径。任务容器替换元数据平行数组时的批处理行为属于历史验收记录。

## 后续连接

`Task` 记录为逐步收拢任务资源提供了单一位置。后续若实现动态任务创建，应再把栈、地址空间和退出回收纳入明确的任务生命周期；不能仅凭本阶段使用 `Vec` 就认为这些资源已经动态化。
