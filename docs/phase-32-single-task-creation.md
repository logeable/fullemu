# 第 32 阶段：单任务创建与失败回滚

## 目标关联

shell 已经可以接受用户输入，但还不能启动一个新的嵌入式用户程序。本阶段先整理任务创建的底层路径，让 shell 和批处理入口共用同一个“创建一个任务”操作。创建过程的资源边界明确后，下一步才适合增加前台 `run <程序名>`。

本阶段沿着 CPU 虚拟化实验逐步演进：已有任务可以被抢占、切换和退出；现在把任务从“启动时一次性批量准备”变成可单独准备的资源组合，但暂不引入运行时命令、后台任务、槽位复用或文件系统。

## 实验问题

**创建一个任务需要多个子系统的资源；如果中途失败，如何确保任务表、地址空间和页帧都回到创建前的状态？**

## 实现范围

- 新增 `kernel::task::creation`，单次创建依次加载程序镜像、分配用户栈、分配内核栈、建立该任务独立的 Sv39 地址空间，最后才把任务记录追加到任务表。
- 任务记录通过 `TaskId` 标识。ID 等于成功追加时的任务表索引；本阶段只追加、不复用，现有最多 8 个任务的限制保留。
- shell 入口和批处理入口均逐个调用相同的创建器。它们仍在启动期创建任务，调度方式及用户可见行为保持原样。
- 用户栈、内核栈在任务记录提交前由局部资源所有者持有，两种栈由各自类型释放 backing 页帧。镜像槽是链接器固定预留的物理区域，不是动态分配资源；每次装载前会清零并覆盖，失败后可直接复用。
- 单个地址空间由 `memory::create_address_space` 建立。页表树尚未构造完整时发生错误，地址空间模块验证并回收本次已分配的页表页；只有建表完整后才发布根页表记录。

## 资源提交顺序

```text
预留任务表容量
  → 加载镜像
  → 分配用户栈
  → 分配内核栈
  → 建立完整地址空间
  → 写入初始陷入帧并追加 Task
```

提交点是任务记录追加。提交点之前任一步返回错误，局部所有者销毁已取得的栈资源；页表模块负责回收内部构造了一半的页表树。镜像槽留在链接器预留区，后续装载会清零覆盖，因此不需要释放物理页帧。任务表容量提前预留，因此发布记录时不会再触发一次可能失败的堆分配。

当前实现通过 `TaskId` 和 `Vec<Task>` 的追加顺序保持 ID 与地址空间索引一致。地址空间记录只在整棵页表建立后追加；创建失败时移除最后一个未投入运行的地址空间记录。任务退出后的记录仍保留，ID 不复用。

## 运行与验收

```sh
make fmt-check
make build
make run BOOT_MODE=shell LOG_LEVEL=info
make run BOOT_MODE=batch LOG_LEVEL=info
```

启动后应正常进入 shell 或批处理。shell 模式仍只启动配置的入口程序；批处理仍装入清单中构建时保留的所有程序。调试日志可检查每个任务的创建记录和独立页表。

## 当前限制

- 创建器尚未由 shell 或 syscall 在运行期调用；用户不能动态启动程序。
- 任务上限仍为 8，任务 ID 和已退出任务记录都不复用。
- 用户镜像位于按程序索引划分的固定物理槽位；同一程序的并发实例尚未支持。
- 本阶段不包含人为失败注入。真实错误返回路径通过局部栈所有者和页表创建器处理已取得的动态资源；固定镜像槽不属于页帧分配器管理的动态资源，后续装载前会清零复用。

## 后续连接

在此基础上可实现 shell 前台 `run <程序名>`：shell 请求创建任务、等待其退出，再恢复 shell。该实验还需明确调度器如何在 shell 等待期间运行新任务、退出状态如何返回，以及固定镜像槽何时可以再次使用；不需要先实现文件系统或后台任务。
